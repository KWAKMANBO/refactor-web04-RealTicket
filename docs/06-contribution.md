# 6. 기여 정리

## 작성 기준

이번 전환과 측정은 **AI 코딩 도구(Claude Code)와 함께** 진행했다. 역할은 다음과 같이 나뉜다.

- **직접 한 것**: 방향 결정, 여러 안 중 선택, 포트폴리오 시나리오 설계, 로컬 검증, 실제 측정, 문제 발견
- **AI가 구현한 것**: 코드·테스트·스크립트·문서 작성

포트폴리오에도 이 구분을 그대로 적는 것을 권장한다. 면접에서는 구현을 직접 설명할 수 있어야 하므로, 아래 [면접 전 체크리스트](#5-면접-전-직접-설명할-수-있어야-할-것)를 꼭 확인할 것.

## 1. 원래 팀 프로젝트(NestJS)에서의 기여

저장소가 얕게 복제되어 있어 **2024-11-28 이후 커밋만** 확인된다. 그 이전 기여는 직접 채워 넣어야 한다.

| 기능 | 내용 | 커밋 |
|---|---|---|

| | 게스트 삭제 | `5570fa9` |

## 2. 이번 전환에서 직접 한 것

### 방향 결정

| 결정 | 내용 |
|---|---|
| 전환 착수 | 백엔드를 Java로 옮기기로 하고 전환 계획 수립을 요청 |
| DB 접근 기술 | JPA 선택 |
| 전환 방식 | 운영 중인 서비스가 아니라는 판단으로 **한 번에 전환** 결정 (점진 전환의 라우팅·병행 운영 비용 제거) |
| 웹 스택 | Spring MVC와 WebFlux의 장단점을 듣고 MVC + 가상 스레드 채택 |
| MOCK_MODE | 실제 사용 여부를 확인한 뒤 제거 결정 |
| 관리자 회원가입 보안 | 세 가지 안(관리자만 허용 / 설정 토글 / 삭제) 중 **설정 토글** 선택 |
| 브랜치 전략 | 전환 브랜치 이름을 `refactor/backend-java-migration`으로 정리, 측정은 운영 코드와 분리된 `bench/seat-performance` 브랜치에서 진행 |
| 측정 기반 | DB 구조 비교가 필요하므로 Flyway를 쓰는 Java 코드 위에서 측정하기로 결정 |

### 포트폴리오 시나리오 설계

- "좌석 1개 = 1행 → 반정규화 → 동시성 문제 → Redis" 흐름의 초안을 직접 작성했다.
- 검토 과정에서 "Redis에 캐싱해서 해결"을 **"Redis로 분리 + 원자적 처리로 해결"**로 인과를 바로잡았다.
- 측정 지표(처리량, p95, 중복 예매 수, DB가 읽은 행 수)와 비교 대상(DB 락, 조건부 UPDATE 포함)을 정했다.

### 실행·검증·측정 (직접 수행)

| 항목 | 내용 |
|---|---|
| 로컬 검증 | PC에서 프런트엔드 + 백엔드를 띄워 동작 확인 |
| Docker 빌드 | PC에서 백엔드 이미지 빌드 성공 확인 (개발 환경에서는 네트워크 제약으로 확인하지 못한 부분) |
| 성능 측정 | MacBook Air M3에서 **4회 반복 측정**, 모든 회차 검증 통과 |
| DB 실행 계획 | `EXPLAIN ANALYZE`로 읽은 행 수 확인 (3,000행 vs 10행, 두 구조 모두 인덱스 사용) |
| 환경 문제 해결 | 포트 충돌(기존 Redis 컨테이너) 정리 |

### 품질을 높인 발견과 질문

| 발견·질문 | 결과 |
|---|---|
| PC에서 `docker-compose.yml`이 없다는 것을 발견 | `.gitignore` 규칙 때문에 커밋에서 빠진 것을 찾아 수정 |
| macOS에서 `run-all.sh`가 멈추는 문제 보고 | macOS bash 3.2의 한글 변수 파싱 문제를 찾아 수정 |
| "지금 오류가 없는 게 맞아?" | 결과 표가 일부 비교의 오류를 보여 주지 않는 허점을 발견 → 오류 열, 회차 검증, 실패 회차 자동 제외 기능 추가 |
| "여러 번 돌려서 검증하는 게 좋을까?" | 중앙값 종합 도구(`aggregate.py`) 추가, 4회 측정으로 결과 신뢰도 확보 |
| "p99를 측정해야 할까?" | 최대 부하 측정의 p99는 공정한 비교가 아님을 정리 → 주장 범위를 처리량·p95로 한정 |

## 4. 학습한 개념

전환과 측정 과정에서 질문하고 정리한 개념이다. 면접에서 그대로 질문받을 수 있다.

| 개념 | 핵심 |
|---|---|
| Flyway | 스키마 변경을 번호 붙은 SQL 파일로 관리. 적용된 파일은 수정하지 않고 새 버전을 추가. 기록 테이블이 없는 기존 DB에서는 시작을 거부 |
| 조건부 UPDATE | `UPDATE ... WHERE reserved = FALSE` 한 문장으로 확인과 변경을 합침. 바뀐 행 수(1/0)로 성공 판단. InnoDB가 행을 잠그고 최신 값으로 조건을 다시 확인하므로 안전 |
| 비관적 락 | `SELECT ... FOR UPDATE`로 행을 잠근 뒤 변경. 안전하지만 왕복이 많음 |
| 원자적 처리 | Redis도 명령을 나눠 보내면 경쟁이 생김. Lua 스크립트는 실행 중 다른 명령이 끼어들 수 없음 |
| p50 / p95 / p99 | 응답 시간 분포의 백분위. p99는 부하 조건에 민감해 같은 부하에서 비교해야 공정 |
| k6 | VU(가상 사용자), 실행 방식(constant-vus, per-vu-iterations), setup/default/teardown, 지표 |
| SSE 연결 끊김 감지 | Tomcat은 데이터를 보내다 실패해야 끊김을 앎 → 주기적 heartbeat 필요 |

## 5. 면접 전 직접 설명할 수 있어야 할 것

구현을 AI가 했더라도, 아래는 코드를 직접 읽고 설명할 수 있어야 한다.

- [ ] **세션 인증 흐름**: `@RequireStatus` → `SessionAuthInterceptor` → `SessionRepository`(Redis Hash). 단계(LOGIN~ADMIN) 비교 방식
- [ ] **`reserve_seat.lua`**: 한 줄씩 읽고, 왜 중간에 다른 요청이 끼어들 수 없는지
- [ ] **`try_enter.lua` / `admit_waiting.lua`**: 정원 초과를 어떻게 막는지, 대기 번호가 겹치지 않는 이유
- [ ] **`SeatsBroadcaster`**: 변경 표시(dirty flag), 30초 전체 전송, 5초 heartbeat, 연결 교체 시 처리
- [ ] **Flyway + `ddl-auto=validate`**: 왜 TypeORM `synchronize`보다 안전한지
- [ ] **동시성 테스트**: `CountDownLatch`로 동시에 출발시키는 방법
- [ ] **측정 설계**: 중복 예매 판정 방법, 공정성 장치(같은 응답·인덱스·자원 제한), p99를 주장하지 않는 이유
- [ ] **MVC vs WebFlux**: JPA가 블로킹이라는 점, `SseEmitter`가 연결당 스레드를 점유하지 않는 이유
- [ ] **한계와 확장**: 서버 한 대 전제, 여러 대로 늘릴 때 필요한 것(분산 락, Redis Pub/Sub)
- [ ] **DB 조건부 UPDATE도 정확한데 왜 Redis인가**: 처리량 3.7배, DB 부하 분리, SSE용 비트맵

## 6. 포트폴리오 역할 기재 예시

> **RealTicket** (팀 프로젝트 → 개인 리팩터링)
> - 팀 프로젝트(NestJS)에서 게스트 모드(생성·삭제·자동 정리)와 예약 시간대 버그 수정을 담당했다.
> - 이후 개인 리팩터링으로 백엔드를 Spring Boot로 전환했다. 기술 선택(JPA, MVC + 가상 스레드, 일괄 전환)과 보안 정책을 결정하고, 구현은 AI 코딩 도구(Claude Code)를 활용했다.
> - 전환 과정에서 정원 초과 입장, 다른 이벤트 입장자 삭제, 관리자 계정 무단 생성 등 20건 이상의 버그·보안 문제를 수정했다.
> - 이전 구조를 재현한 벤치마크를 설계하고 직접 4회 측정해, 반정규화(처리량 6.9배)와 Redis + Lua 원자 처리(중복 예매 0건, DB 락 대비 처리량 4.2배)의 효과를 검증했다.
