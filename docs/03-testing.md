# 3. 테스트와 검증

## 전략

- **실제 MySQL·Redis로 테스트**: Testcontainers로 테스트마다 실제 DB와 Redis를 띄운다. Lua 스크립트와 Flyway 마이그레이션까지 진짜 환경에서 검증된다.
- **컨텍스트 하나를 공유**: 공통 기반 클래스(`IntegrationTest`)로 모든 통합 테스트가 같은 Spring 컨텍스트·컨테이너를 재사용하고, 테스트마다 DB 테이블과 Redis를 비운다.
- **스키마 검증**: 애플리케이션이 뜨는 것 자체로 "Flyway가 만든 스키마 = JPA 엔티티"가 확인된다 (`ddl-auto=validate`).

## 동시성 테스트

실제 스레드를 동시에 출발시켜(`CountDownLatch`) 경쟁 조건을 재현한다.

| 테스트 | 조건 | 기대 결과 |
|---|---|---|
| 같은 좌석 동시 선점 | 30명이 같은 좌석 | 1명만 성공 |
| 한 사람의 동시 다중 선점 | 인원 2명, 좌석 6개 동시 요청 | 정확히 2개만 성공 |
| 동시 입장 요청 | 40명, 정원 5 | 5명 입장, 35명은 1~35번을 겹치지 않게 받음 |
| 동시 이탈 | 좌석 선택 중 3명이 동시에 떠남, 대기 10명 | 정확히 3명만 입장 |

## 실제 서버 SSE 연결 종료 테스트

MockMvc로는 "브라우저가 연결을 끊는 상황"을 만들 수 없어, 실제 HTTP 서버를 띄우고(`RANDOM_PORT`) Java `HttpClient`로 좌석 SSE에 연결한 뒤 연결을 끊는다.

- 첫 SSE 데이터로 좌석 상태를 받는다.
- 좌석을 선점한다.
- 클라이언트를 닫는다.
- 서버가 heartbeat 전송 실패로 끊김을 감지해 **선점 좌석을 풀고 사용자를 LOGIN으로 돌리는지** 확인한다.

## 프런트엔드 연동 E2E (Playwright)

실제 프런트엔드(`front/`, 수정 없음)를 Java 서버에 붙여 브라우저로 확인했다.

| 시나리오 | 결과 |
|---|---|
| 게스트 로그인 → 회차 선택 → 입장 → 캡차 → 인원 → 좌석 → 예매 확정 | 성공, 결과 화면의 좌석·금액 정확 |
| A가 잡은 좌석이 B 화면에 실시간으로 "선택 불가" | 확인 |
| 정원(2명) 초과 시 C는 대기 화면 ("내 순서 1번") | 확인 |
| A가 탭을 닫으면 C가 자동으로 좌석 화면으로 이동 | 약 9초 후 이동 |
| 상단 메뉴에서 예매 내역 조회·취소 | 확인 (soft delete) |

캡차는 자동 입력이 불가능해, 테스트 브라우저 안에서만 캡차 모듈 응답을 바꿔 통과시켰다 (프런트 코드는 그대로).
