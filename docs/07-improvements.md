Java 전환과 성능 측정 이후의 코드를 다시 분석해 찾은 개선 사항이다. 우선순위는 **실제 문제가 될 수 있는 것(🔴) → 구조·성능 개선(🟡) → 사소한 정리(🟢)** 순서다.

## 🔴 실제 문제가 될 수 있는 것

### 1. 캡차를 브라우저에서만 검증한다

- **근거**: 캡차 생성·검증이 `front/src/components/Captcha/index.tsx`(`react-simple-captcha`)에서만 일어나고, 백엔드에는 캡차 관련 코드가 없다.
- **영향**: 매크로가 API(`GET /booking/permission/{id}`, `POST /booking`)를 직접 호출하면 캡차를 건너뛴다. README의 "매크로 방지 문자로 부하 분산" 기능이 사실상 동작하지 않는다. 예매 서비스의 핵심 방어선이다.
- **개선**
  - 서버에서 캡차 문제를 만들어 Redis에 정답을 짧은 TTL로 저장하고, 입장 허가(`permission`) 전에 검증한다. 통과하면 세션에 "캡차 통과" 표시를 남긴다.
  - 사용자·IP별 요청 횟수 제한(rate limit)을 입장 요청과 좌석 선점에 적용한다 (Redis 고정 윈도 또는 토큰 버킷).
- **검증**: 캡차 없이 API를 직접 호출하면 거부되는지, 제한을 넘는 요청이 429를 받는지 통합 테스트.
- **프런트 영향**: 캡차 이미지를 서버에서 받아 표시하도록 수정 필요.

### 2. 서버를 재시작·배포하면 좌석이 잠긴 채 남을 수 있다

- **근거**: 좌석 선택 중 정보(`in-booking:{e}:sessions`, `in-booking:{e}:session:{sid}`, `:seats`)에 만료 시간이 없다 (`domain/booking/repository/InBookingRepository.java`). 좌석은 "SSE 연결이 끊겼다"는 신호(`SeatsSubscriptionClosedEvent`)로만 풀린다.
- **영향**: 재시작하면 서버 메모리의 SSE 연결이 모두 사라진다. 그 사이 탭을 닫은 사용자는 다시 연결하지 않으므로 "끊김" 신호가 영영 오지 않는다. 그 사용자의 **선점 좌석과 좌석 화면 자리가 예매 마감 때까지 잠긴다.**
- **개선**: 입장 세션 정리(`EnteringGcScheduler`)와 같은 방식으로 "생존 확인"을 둔다.
  - 좌석 선택 중 세션을 ZSet(`score = 마지막 확인 시각`)으로 관리한다.
  - heartbeat 전송에 성공할 때마다 시각을 갱신한다.
  - 주기 작업이 일정 시간(예: 30초) 확인되지 않은 세션을 `leave_in_booking`과 같은 방식으로 정리한다.
- **검증**: 좌석을 선점한 상태에서 연결 정보를 강제로 지워(재시작 상황 재현) 일정 시간 안에 좌석이 풀리는지 통합 테스트. "재시작 후 N초 안에 좌석 해제"로 수치화 가능.

### 3. 좌석 선택 시간에 제한이 없다

- **근거**: 좌석 선택 중 세션에 시작 시각이나 기한이 없다.
- **영향**: 좌석 화면을 열어 두기만 하면 좌석을 무기한 점유할 수 있다. 실제 예매 서비스는 보통 5~10분 안에 결제하지 않으면 좌석을 해제한다.
- **개선**: 좌석 선택 시작 시각을 기록하고, 제한 시간(설정값, 예: 10분)이 지나면 2번의 정리 작업에서 함께 해제한다. 남은 시간을 SSE로 알려 주면 프런트에서 카운트다운을 표시할 수 있다.
- **검증**: 제한 시간을 짧게 둔 테스트에서 시간이 지나면 좌석이 해제되고 상태가 LOGIN으로 돌아가는지.

### 4. CI가 실행되지 않고, 배포가 비밀번호 기반이다

- **근거**: `.github/workflows/ci.yml`은 `main`에 push될 때만 실행되는데, 원격 저장소에 `main` 브랜치가 없다 (`dev`만 있음). 전환 때 추가한 백엔드 테스트 단계도 실행되지 않는다. 배포는 `sshpass`로 서버 비밀번호를 넘긴다.
- **영향**: 테스트가 자동으로 돌지 않아 회귀를 잡지 못한다. 비밀번호 기반 SSH는 유출 위험이 크다.
- **개선**
  - 테스트 워크플로를 분리해 PR과 `dev` push에서 실행한다.
  - 배포는 SSH 키(GitHub Secrets) 또는 GitOps(이미지 태그 갱신 → Argo CD)로 바꾼다.
  - Gradle·Docker 캐시를 적용해 실행 시간을 줄인다.
- **검증**: PR을 열어 테스트가 자동으로 실행되는지 확인.

## 🟡 구조·성능 개선

### 5. 좌석 SSE가 "변경분"이 아니라 "전체 좌석"을 보낸다

- **근거**: 좌석이 하나만 바뀌어도 전체 `seatStatus`(구역별 boolean 배열)를 JSON으로 보낸다 (`domain/booking/sse/SeatsBroadcaster.java`). 프런트는 `front/src/pages/ReservationPage/SeatMap.tsx`에서 이 형식을 받는다.
- **영향**: 3,000석 기준 한 번에 **약 15KB**다. 1,000명이 보고 있으면 0.5초마다 약 15MB, 초당 약 30MB를 내보낸다.
- **개선** (프런트 수정 필요)
  - 전체 상태를 비트맵 그대로 Base64로 보내면 **약 500바이트(약 97% 감소)**다.
  - 더 나아가 변경된 좌석만 보내고, 주기적으로(30초) 전체 상태를 보내 어긋남을 바로잡는다.
- **검증**: k6나 테스트로 메시지 크기와 초당 전송량을 전후 비교.
- **⚠ 포트폴리오 문구 주의**: 슬라이드의 "좌석 현황은 SSE로 **변경분만** 보냈습니다"는 사실과 다르다. Nest와 Java 모두 "**변경이 있을 때** 전체를 보낸다". 문구를 고치거나 이 개선을 실제로 적용할 것.

### 6. 한 사용자가 여러 공연에 동시에 대기·입장할 수 있다

- **근거**: `BookingService.requestAdmission`은 예매 대상 이벤트만 바꾸고, 이전 이벤트의 대기 번호·입장 자리·좌석 선택 세션은 정리하지 않는다.
- **영향**: 이전 공연의 자리가 다른 사람의 입장을 막는다.
- **개선**: 새 입장 요청 시 이전 대상 이벤트가 있으면 그 이벤트에서 대기열 제거·입장 취소·좌석 해제를 먼저 수행한다.
- **검증**: A 공연 입장 후 B 공연에 입장하면 A 공연의 자리가 비는지.

### 7. 대기 중 탭을 닫아도 대기열에 남는다

- **근거**: 대기열 SSE가 끊겨도 아무 처리를 하지 않는다 (`domain/booking/sse/WaitingBroadcaster.java`의 끊김 처리가 비어 있음).
- **영향**: 떠난 사람의 차례가 오면 아무도 쓰지 않는 입장 자리가 입장 유효 시간(prod 2분) 동안 잡혀, 뒤 사람들이 그만큼 더 기다린다.
- **개선**: 대기열 SSE가 끊기면 유예 시간(재연결 여유, 예: 10초)을 두고, 그 안에 돌아오지 않으면 대기열에서 제거한다. 브라우저의 자동 재연결과 구분하기 위해 유예 시간이 필요하다.
- **검증**: 대기 중 연결을 끊고 유예 시간이 지나면 대기열에서 빠지는지.

### 8. 관측 수단이 없다

- **근거**: actuator `health`만 열려 있다 (`application.yml`).
- **영향**: 예매 오픈 순간 무슨 일이 일어나는지 볼 수 없다. 병목·장애를 사후에 추적하기 어렵다.
- **개선**: Micrometer + Prometheus 지표를 노출하고 Grafana 대시보드를 만든다.
  - SSE 연결 수(좌석·대기열), 이벤트별 대기열 길이·입장·좌석 선택 인원
  - 좌석 선점 성공/충돌/거부 수, Lua 실행 지연
  - HTTP 지연(p95/p99), JVM·커넥션 풀
- **검증**: 측정 환경(`bench/`)에 Prometheus·Grafana를 붙여 부하 중 지표가 보이는지. 측정 결과 화면을 포트폴리오에 쓸 수 있다.

### 9. `BookingService`의 역할이 많고, Lua 결과를 숫자로 분기한다

- **근거**: `domain/booking/service/BookingService.java`(262줄)가 입장, 좌석 선점, 이탈, 입장 정리, 관리자 기능, 예매 확정 보조를 모두 맡는다. Lua 결과를 `-1`~`-5` 같은 숫자로 `switch`한다.
- **개선**
  - 입장(`AdmissionService`) / 좌석 선택(`SeatSelectionService`) / 관리자(`BookingAdminService`)로 나눈다.
  - 저장소 계층에서 Lua 결과를 의미 있는 enum(`ReserveResult.ALREADY_TAKEN` 등)으로 바꿔 돌려준다.
- **검증**: 기존 테스트가 그대로 통과하는지 (동작 변화 없는 리팩터링).

### 10. 구역 순서를 두 곳에서 관리한다

- **근거**: 구역이 어느 장소에 속하는지는 `sections.place_id`, 순서는 `places.sections` JSON 배열로 따로 저장한다 (`domain/place/entity/Place.java`).
- **영향**: 둘이 어긋나면 좌석 번호(sectionIndex)가 틀어진다. 구역을 추가·삭제할 때 두 곳을 함께 맞춰야 한다.
- **개선**: `sections`에 순서 컬럼(`section_order`)을 두고 JSON 배열을 없앤다 (Flyway `V2`). 순서 조회는 `ORDER BY section_order`.
- **검증**: 구역 추가 후 좌석 정보의 구역 순서와 예매 좌석 이름이 맞는지.

## 🟢 사소한 정리

| 항목 | 근거 | 개선 |
|---|---|---|
| 에러 응답에 내부 메시지 노출 | 요청 본문 파싱 실패 등에서 Spring 기본 메시지가 그대로 나감 (`GlobalExceptionHandler.handleExceptionInternal`) | 일반 메시지로 바꾸고 상세 내용은 로그에만 |
| 재시작 시 관리자 설정 초기화 | 시작할 때 좌석 화면 기본 최대 인원을 설정값으로 덮어씀 (`OpenBookingService.onApplicationReady`, Nest와 동일) | 값이 없을 때만 설정 |
| Docker 이미지가 root로 실행, 컨테이너 안에 로그 파일 기록 | `back/Dockerfile`, `logback-spring.xml` | 일반 사용자 실행, 컨테이너 환경에서는 표준 출력만 |
| 도메인 간 DTO 의존 | `event`가 `program.dto.PlaceResponse` 사용 | 공통 위치로 이동 |
| 프런트엔드 정리 | 쓰지 않는 mock 상수·함수, `npm audit` 취약점 | 삭제, 안전한 범위에서 의존성 갱신 |
| 서버 한 대 전제 | 스케줄러, SSE 채널이 서버 메모리에 있음 | 확장 시 분산 락(ShedLock), 서버 간 좌석 변경 알림(Redis Pub/Sub) |
