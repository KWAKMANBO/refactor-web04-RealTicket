# 4. 성능 측정

좌석 데이터 구조와 동시성 처리 방식의 효과를 수치로 확인하기 위해, 이전 구조를 재현해 같은 조건에서 비교했다.

- 브랜치: `bench/seat-performance`
- 실행 방법·도구 설명: [`bench/README.md`](../bench/README.md)

## 측정 이야기 (포트폴리오 흐름)

1. **문제**: 좌석 1개를 1행으로 저장해, 좌석 배치를 조회할 때마다 좌석 수만큼 행을 읽고 JOIN했다.
2. **해결**: 좌석 배치는 공연 기간 동안 바뀌지 않으므로 구역별 배열로 묶었다(반정규화). → 대신 좌석 하나만 바꾸기 어려워졌다.
3. **새 문제**: 예매 중 계속 바뀌는 좌석 상태를 동시에 선점하면 중복 예매가 생긴다.
4. **해결**: 바뀌지 않는 배치(DB)와 실시간 상태(Redis 비트맵)를 나누고, 상태 변경은 Lua로 원자적으로 처리했다.

"Redis에 캐싱해서 해결"이 아니라 **"Redis로 옮기기만 해서는 오히려 악화됐고, 원자적 처리가 핵심이었다"**는 것을 측정으로 보였다.

## 측정 설계

### 비교 대상

| 비교 | 대상 |
|---|---|
| 1. 좌석 배치 조회 | 구역별 JSON 배열(운영) vs 좌석 1개 = 1행 |
| 2-1. 같은 좌석 동시 선점 | DB 단순 처리 / DB 비관적 락 / DB 조건부 UPDATE / Redis 단순 처리 / Redis + Lua(운영) |
| 2-2. 좌석 선점 처리량 | 중복 예매가 없는 세 방식 (DB 비관적 락, DB 조건부 UPDATE, Redis + Lua) |

### 운영 코드와 분리

- `bench` 프로필에서만 측정용 테이블(Flyway `db/bench/V100__bench_tables.sql`)과 API(`/bench/**`)가 열린다.
- 실수로 운영에 합쳐져도 운영 DB에는 측정용 테이블이 생기지 않는다.

### 공정성을 위한 장치

| 장치 | 내용 |
|---|---|
| 같은 응답 | 두 좌석 구조가 **완전히 같은 JSON**을 만드는지 테스트로 확인 |
| 비교 대상도 최적화 | 좌석 1개 = 1행 테이블에 인덱스 적용, JOIN 한 번으로 조회 (실행 계획으로 인덱스 사용 확인) |
| 같은 DB에 두 구조 공존 | 같은 데이터를 양쪽에 넣고 읽는 경로만 바꿈 (스키마를 바꿔 가며 재시작하지 않음) |
| 자원 고정 | Docker로 백엔드 CPU 2·힙 1GB, MySQL CPU 2, Redis CPU 1 제한 |
| 워밍업 | 조회 측정 전 요청 200번 |
| 측정 범위 통일 | 좌석 선점은 "확인 + 예약"만 비교 (세션 확인 제외) |
| 좌석 순환 | 처리량 측정에서 좌석이 다 차지 않도록 성공하면 바로 해제 |
| 중복 예매 판정 | 서버가 "이미 점유된 좌석에서 또 성공"한 경우를 직접 집계 |
| 결과 검증 | 회차마다 오류 0건, 안전한 방식의 중복 예매 0건·성공 수 = 좌석 수를 자동 판정, 실패 회차는 종합에서 제외 |
| 반복 | 4회 측정 후 중앙값 |

### 도구

- k6 시나리오 3개 (`layout.js`, `race.js`, `throughput.js`)
- `run-all.sh`: 데이터 생성 → 세 비교 → 결과 표·검증까지 한 번에
- `aggregate.py`: 여러 회차의 중앙값(최소~최대)과 배율
- `explain.sh`: DB 실행 계획(읽은 행 수) 확인

## 측정 환경

- MacBook Air M3 (8코어, 16GB), macOS 26.6, Docker Desktop
- 백엔드 CPU 2개·힙 1GB, MySQL CPU 2개, Redis CPU 1개, DB 커넥션 풀 10
- 공연장 3,000석 (구역 10개 × 300석)
- 조회·처리량: 동시 사용자 50명 × 30초 / 동시 선점: 좌석 100개 × 각 100명
- **4회 반복, 모든 회차 검증 통과**

## 결과 (4회 중앙값, 괄호는 최소~최대)

### 1. 좌석 배치 조회

| 구조 | 처리량 (req/s) | p50 (ms) | p95 (ms) | p99 (ms) |
|---|---|---|---|---|
| 좌석 1개 = 1행 | 474.0 (432.3~544.2) | 100.87 | 165.28 | 195.50 |
| 반정규화 | **3,263.3** (2,232.2~4,065.3) | 12.01 | **38.89** | 57.50 |

DB 실행 계획 (`EXPLAIN ANALYZE`, 3,000석, 두 쿼리 모두 인덱스 사용):

| 구조 | 읽은 행 | DB 실행 시간 | 저장 공간 (공연장 1개당 근사) |
|---|---|---|---|
| 좌석 1개 = 1행 | 3,000행 + JOIN + 정렬 | 2.46ms | 약 472KB |
| 반정규화 | **10행** | **0.11ms** | 약 20KB |

### 2-1. 같은 좌석 동시 선점 (좌석 100개 × 각 100명)

| 방식 | 성공 | 중복 예매 |
|---|---|---|
| DB 단순 처리 | 354 (329~373) | **254 (229~273)** |
| DB 비관적 락 | 100 | 0 |
| DB 조건부 UPDATE | 100 | 0 |
| Redis 단순 처리 | 4,597 (1,122~6,127) | **4,497 (1,022~6,027)** |
| **Redis + Lua** | 100 | **0** |

### 2-2. 좌석 선점 처리량

| 방식 | 처리량 (req/s) | p50 (ms) | p95 (ms) | p99 (ms) |
|---|---|---|---|---|
| DB 비관적 락 | 2,192.8 (2,005.6~2,275.9) | 10.68 | 17.74 | 26.24 |
| DB 조건부 UPDATE | 2,504.0 (2,239.2~2,602.8) | 9.18 | 15.44 | 22.62 |
| **Redis + Lua** | **9,193.0** (8,026.6~9,989.3) | **2.14** | **4.43** | 19.15 |

## 핵심 수치

- 반정규화: 읽는 행 **3,000 → 10**, API 처리량 **6.9배**, p95 **76% 감소**
- Redis로 옮기기만 하면 중복 예매가 **1,022~6,027건**으로 DB 단순 처리(229~273건)보다 **모든 회차에서 더 많았음**
- Redis + Lua: **4회 모두 중복 예매 0건**
- Redis + Lua: DB 비관적 락 대비 처리량 **4.2배**, p95 **75% 감소** / DB 조건부 UPDATE 대비 **3.7배**, p95 **71% 감소**

## 해석과 한계

- **p99는 주장하지 않는다.** 처리량 측정은 각 방식을 한계까지 몰아 서로 다른 부하에서 잰 값이다. redis-lua의 p99가 4회 내내 약 19ms로 일정했는데, 초당 9천 건 이상을 CPU 2개로 처리하며 포화된 영향으로 보인다. 공정한 p99 비교는 모든 방식에 같은 부하(예: 초당 1,500건)를 걸어야 한다.
- **Redis 단순 처리가 더 나쁜 이유**: Redis가 빨라 같은 시간에 더 많은 요청이 "읽기 → 쓰기" 사이로 끼어들고, 범위 확인·읽기·쓰기가 세 번의 왕복으로 나뉘어 틈이 넓다.
- **DB 비관적 락과 조건부 UPDATE의 차이가 작은 이유**: 무작위 좌석 3,000개에 요청이 분산돼 같은 행을 두고 잠금 경쟁이 거의 없었다. 인기 좌석에 몰리면 차이가 커질 것으로 예상된다.
- **DB 조건부 UPDATE도 정확하다.** Redis를 택한 근거는 처리량(3.7배), 예매 트래픽의 MySQL 분리, 0.5초마다 전체 좌석을 보내는 SSE에 비트맵이 유리하다는 점이다. 트래픽이 크지 않다면 조건부 UPDATE도 좋은 선택이다.
- **절대값보다 상대 비교**: Docker Desktop의 네트워크 계층과 팬이 없는 MacBook Air의 열 제한이 절대 수치에 영향을 준다. 같은 회차 안에서 모든 방식이 같은 조건이고, 가장 빠른 redis-lua가 열이 가장 많이 쌓인 마지막 순서에 측정되어 결론은 보수적인 쪽이다.
- **재현 구조**: 좌석 1개 = 1행 구조와 단순 처리 방식은 비교를 위해 재현한 것이다.
- **측정 범위**: 운영 API(`POST /booking`)는 여기에 세션 조회·인원 확인이 더해진다.

## 측정 도구 개선 이력

| 문제 | 발견 | 조치 |
|---|---|---|
| `docker-compose.yml`이 커밋에서 빠짐 | PC에서 실행 시 파일 없음 | 루트 `.gitignore`의 compose 무시 규칙에 측정용 파일만 예외 추가 |
| macOS 기본 bash(3.2)에서 스크립트 중단 | PC 실행 시 `unbound variable` | 변수를 `${VAR}`로 감싸 한글이 변수 이름에 섞이지 않게 함 |
| 결과 표에 일부 비교의 오류가 보이지 않음 | "오류가 없는 게 맞나?" 질문 | 모든 비교에 오류 열, 회차 검증 항목, 실패 회차 자동 제외 |
| 최신 k6(v2.3)와의 호환 | 사전 점검 | v0.57, v2.3에서 동작 확인, 결과 집계를 k6 로그가 아닌 서버 집계 JSON으로 |
| 포트 충돌(6379) | PC 실행 시 컨테이너가 `Created`에 멈춤 | 기존 컨테이너 정리, README에 안내 추가 |
| 실행 계획 출력이 한 줄로 이어짐 | 결과 확인 중 | `mysql -r`로 출력, `explain.sh`로 자동화 |
